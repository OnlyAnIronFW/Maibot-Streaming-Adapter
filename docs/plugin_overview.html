maibot_bilibili_live_adapter / 运行流程与机制详解

MaiBot 的 Input-only（仅输入）B 站直播适配插件：从直播间采集弹幕注入 MaiBot 主链路， 将 MaiBot 回复在本机渲染为「语音 + 绿幕字幕 + Live2D / 立绘 / 音效」直播表现，但不把回复写回 B 站。 配套独立服务端 livehub 实现多 AI 共享直播间。

插件 ID: maibot.bilibili-live-adapter manifest v2 · host 1.0.0–1.99.99 SDK 2.3.0–2.99.99（宿主 1.1.3 / SDK 2.7.1 实测通过） 直播间 4538234 / 测试房 22889518
① 全局架构 ② 启动流程 ③ 输入链路 ④ 回复输出链路 ⑤ livehub 专题 ⑥ 模块地图 ⑦ 配置体系 ⑧ 兼容修复 ⑨ 测试与运维

01全局架构：两条链路 + 一个编排核心

插件整体呈「输入链路 → MaiBot 主链路 → 输出链路」的环形结构。输入链路把直播事件注入 MaiBot； 输出链路截获 MaiBot 回复并驱动本地渲染。所有模块由 plugin.py（约 7900 行）统一编排。

┌──────────────── 输入链路（Input-only）────────────────┐ B站弹幕 WS ─┐ livehub 事件─┼─→ bilibili_transport / hub_input_client 本地语音ASR ─┤ │ 规范化 live event（去重/筛选/采样） 视觉/视频 ─┘ ▼ event_router（事件路由 + 窗口缓冲 + 空闲话题） ▼ interaction_planner（弹幕优先级采样） ▼ message_codec（→ 模拟 QQ 群消息 MessageDict） ▼ ctx.gateway.route_message ──→ MaiBot 主链路 ┌──────────────── 输出链路（本地表现，不回写B站）────────┐ MaiBot 回复 ──→ @MessageGateway(duplex) handle_bilibili_gateway │ 串行化投递（打断/语音租约协调） ┌─────────┬─────┼──────┬──────────┬─────────┐ ▼ ▼ ▼ ▼ ▼ ▼ TTS 字幕WebUI Live2D 音效板 立绘 Hub转发 (GPT-SoVITS)(绿幕OBS) (口型/表情) (关键词/LLM) (LLM选表情) (多AI协调) ┌──────────────── 编排核心 ────────────────┐ plugin.py: BilibiliLiveAdapterPlugin on_load / on_unload / on_config_update → _restart_runtime 装配 transport / router / live2d / tts / soundboard / livehub 联动 ┌──────────────── 配套服务端（独立进程）────────────────┐ livehub（python -m livehub，端口 18190） B站采集 → 事件环(seq) → HTTP轮询 + WS广播 → 多bot共享 参与者presence / 语音互斥队列 / 回复转发
核心设计原则
  • 输入：高频采集、低频理解 —— 弹幕经去重/筛选/窗口缓冲后批量注入，避免刷屏冲击主链路
  • 输出：回复投递全程串行化（_run_serialized_delivery），支持打断、Hub 语音租约、分段渲染
  • Input-only：duplex 网关但从不把回复发回 B 站，只驱动本地表现（OBS 推流侧消费）
  • 模拟群聊：弹幕注入为「QQ 群消息」形态（group_id=房间号），复用 MaiBot 群聊理解能力

02启动与生命周期流程

宿主加载 manifest → Runner 子进程执行 on_load → 装配运行时 → 常驻。配置热重载走同一条重建路径。

1
Manifest 校验宿主侧
宿主 manifest_validator.load_from_plugin_path() 校验 _manifest.json：版本区间（host ≤1.99.99 / SDK 2.x）、capabilities 声明（host.route_message 等 5 项）。失败则插件直接不加载。
▼
2
Runner 子进程启动宿主侧
宿主 supervisor 拉起 Runner 进程，注入 SDK 环境；插件模块 plugin.py 被 import（此时顶层只做依赖导入，不做重活 —— A_memorix 等重资源全部延迟到使用点）。
▼
3
on_load → _restart_runtime
读取配置（_load_settings）→ _stop_runtime() 清理旧运行时 → livehub 联动（若 auto_start_livehub=true 且探测不在线，则 create_subprocess_exec 拉起 python -m livehub 并轮询就绪）→ 逐项装配。
▼
4
运行时装配（按配置开关）
B站 transport（4 路并行 WS）→ event_router → HubInputClient（WS 订阅 + HTTP 轮询）→ Live2D 控制器（adaptive/soullink/embodied 三 scheme）→ TTS provider → 字幕 WebUI 服务 → 音效板 → 立绘控制器 → 网关状态上报 update_state(ready)。
▼
5
组件注册
@Tool 视觉/视频/Live2D 调试等工具、@API 接口、@HookHandler 三个钩子（send_service.before_send、maisaka.planner.before_request/after_response）随类装饰器注册进宿主。
▼
6
常驻运行 / 热重载 / 卸载
配置变更触发 on_config_update → _restart_runtime（先停后起，livehub 子进程一并重建）；on_unload → _stop_runtime 逆序停止全部组件并关闭自己拉起的 livehub（不动手动启动的实例）。
livehub 联动细节（_maybe_auto_start_livehub）
  • 探测：应用层 GET /api/health 校验 success 字段（2s 超时，带 auth_token 时附 Bearer 头）—— 避免端口被无关程序占用的误判
  • 拉起：sys.executable -m livehub --host --port --room-id，cwd=插件目录，日志重定向 data/logs/livehub.log
  • 并发保护：_livehub_start_lock 串行化 start/stop，防止 on_load 与 on_config_update 竞争
  • 就绪等待：20 × 0.5s 轮询；进程早退则读日志告警并清理句柄

03输入链路：从弹幕到 MaiBot 群聊消息

四个事件来源汇聚到同一条注入管道。协议编解码由插件与 livehub 共享的 livehub/bilibili_protocol.py 单一实现提供。

3.1 事件来源

来源模块机制
B站弹幕bilibili_transport / livehub/capturegetConf 获取服务器+token → 4 路并行 WS → auth → 30s 心跳 → zlib 包解析 → DANMU_MSG / SC / 礼物 / 舰长 规范化
Hub 事件hub_input_clientWS 订阅 + HTTP 轮询双通道拉取 livehub 事件环；首次 sync 建立去重基线（不交付历史），此后按 seq 递增交付
本地语音local_voice_* 4 模块麦克风连续采集 + 实时 ASR（sherpa-onnx），转 local_voice 事件
视觉/视频vision_tool / video_watch桌面截图视觉总结；空闲时 B 站视频观看与解说（Tool 触发式）

3.2 处理管道（event_router）

a
去重与清洗
event_id 窗口去重（多路 WS 同弹幕只留一份）、非法字段过滤、类型白名单（danmaku/super_chat/gift/guard/hub_local_input/hub_bot_reply）
▼
b
窗口缓冲与批量注入
弹幕先进缓冲窗口，按节奏批量投递，避免高频刷屏；付费事件（SC/舰长）走高优先级通道
▼
c
采样选择（interaction_planner）
按优先级与配额挑选本批次注入哪些弹幕 —— 低频高质，保护 MaiBot 注意力
▼
d
消息构造（message_codec）
构造 MessageDict：group_info.group_id = 房间号、group_name = bilibili_live_<房间>、user_info = 弹幕用户、additional_config 携带 platform_io_account_id/scope 路由键 + maibot_memory_platform=qq + maibot_local_render_only=True。即弹幕被模拟为 QQ 群聊消息进入 MaiBot。
▼
e
注入网关
ctx.gateway.route_message()（能力名 host.route_message）→ MaiBot 主链路按普通群消息处理（意图/记忆/回复决策全套流程）

3.3 空闲话题（idle topic）

直播间冷场时，topic_extension_client + topic_state 维护话题池：从历史弹幕/视频观看记忆中提取可聊话题， 经 event_router 以低优先级注入，让 bot 在无人发言时也能自然开口。话题状态持久化于 data/live_topic_state.json。

04回复输出链路：本地直播表现

MaiBot 的回复经 duplex 网关进入插件后，走串行化投递，依次驱动各渲染通道。全程不回写 B 站。

1
网关接收duplex
@MessageGateway(route_type="duplex") 的 handle_bilibili_gateway 收到 MaiBot 回复；按 session_id == _build_live_chat_id() 识别直播会话
▼
2
串行化队列
_run_serialized_delivery 保证回复按序渲染；新回复到来时可打断当前播报；与 Hub 语音租约联动（见 ⑤）
▼
3
并行渲染通道
TTS（tts_provider GPT-SoVITS 合成 → audio_output sounddevice 播放）· 字幕（subtitle_webui 绿幕页面 + translation_client 双语翻译，OBS 抠像叠加）· Live2D（口型时间线 + 表情/动作参数控制）· 音效板（关键词即时触发 + LLM 语义选择）· 立绘（LLM 选表情 → _tachie_window.py 子进程显示）· Hub 转发（/api/client/reply 通知其他 bot）
▼
4
渲染完成回调
语音播完 → 释放语音租约（speak-complete）→ 队列下一条；Live2D 回到默认姿态

4.1 Live2D 三种 scheme

scheme模块机制
adaptivelive2d_adaptive/纯参数控制：语义映射（semantic_mapper）→ 表情/动作/口型参数写入模型内存桥；capability_probe 探测模型支持的能力面
soullinklive2d_shell_* + live2d_soullink_vendorSoulLink Shell 桌面窗口（live2d_shell_window_process.py 子进程渲染），插件经 live2d_shell_protocol 消息驱动
embodiedlive2d_adaptive/embodied.py连接宿主 avatar-state WebSocket 获取具身状态流（token 取自插件配置），驱动鼠标跟随（mouse_follow）、本地口型（local_lipsync）、语音时间线对齐

4.2 Hook 拦截

三个 @HookHandler（mode=BLOCKING, order=LATE, error_policy=LOG）： send_service.before_send（回复出站前拦截 → 转入本地渲染管道）、 maisaka.planner.before_request / after_response（规划上下文注入直播状态，如「当前正在直播、观众正在讨论 XX」）。

05livehub 服务端专题：多 AI 共享直播间

多个 MaiBot 实例共享同一个直播间时，由 livehub（独立进程，python -m livehub）统一采集 B 站弹幕并广播， 各 bot 作为「参与者」接入。协议与插件客户端 hub_input_client / plugin.py 逐字段对齐。

核心机制
  • 事件环：每条事件分配递增 seq，deque 历史窗口（history_limit），HTTP 轮询与 WS 推送双通道
  • 参与者管理：presence 心跳（/api/client/presence）注册 bot，超时自动离线；上限 128
  • 语音互斥：speak-request 立即授予或排队（队列上限 128）→ speak-complete 释放并移交队首 → 超时自动释放（expected_duration + 宽限秒）
  • 回复转发：/api/client/reply（兼容插件 JsonBridgeClient 包装形态）→ bot_reply 事件广播
  • 手动注入：/api/inject → local_inject 事件（调试/外部输入源）
  • 认证：可选 Bearer token（hmac 恒定时间比较），失败 401 并记审计日志
可靠性设计
  • 多路去重：并行 WS 收到相同弹幕按 event_id 10s 窗口去重
  • 指数退避：断线重连 base×2^(n-1) 封顶 60s，连接稳定自动复位
  • 接收超时联动：receive 超时 = max(60s, 心跳×2+5)，冷清直播间不误断
  • 慢客户端保护：WS 广播 gather 并行、单客户端 5s 超时剔除；广播任务积压 >32 丢弃（事件仍可轮询）
  • 启动回滚：服务启动任一步失败自动清理已启动组件
  • 配置钳制：端口/房间/超时等非法值回退默认并告警，永不带病启动
